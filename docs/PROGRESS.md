## Decisions log (append-only — record anything non-obvious you decided)
- 2026-07-09: **Money — decouple rider pay from the customer delivery charge** (branch `fix/checkout-delivery-fee`, **migration 037**). Diagnosis first: the "riders earn ₹0" report was NOT a calc bug — the free-delivery threshold (`free_delivery_above=999`) correctly zeroes the CUSTOMER delivery fee on ₹999+ orders, but `orders.delivery_fee` was ALSO the rider's pay, so the rider earned nothing for the same trip (confirmed in the data: sub<999 → fee 49, sub≥999 → fee 0). Owner chose the "separate rider-pay config" option. Fix: `system_settings.rider_fee` (default 40, platform cost) + `orders.rider_fee` stamped at checkout **always** (no waiver) + backfill of existing orders; agent Earnings/History + admin agent-payouts `compute.ts` repointed from `delivery_fee` → `rider_fee` (renamed `CompletedDelivery.deliveryFee` → `riderFee` throughout for clarity); `delivery_fee` stays the customer charge. Admin System Settings → Commission & Payouts gains a "Rider Pay per Delivery" field. **Deliberately did NOT touch `available_deliveries()`** to show rider_fee on the offer card — that RPC was just changed in the unmerged 036, so re-touching it across branches risks migration-ordering regressions (037 would need 036's freshness filter + offer_expiry column to exist); deferred to a follow-up after #36 merges. typecheck (customer/agent/admin) passes; **037 pending apply + a browser check (new order stamps rider_fee, earnings show it) is Dilip's step.**

## Realtime / cross-panel
> **⚠️ Architecture note (2026-06-27): cross-panel pop-up alerts now ride on the
> `notifications` table, NOT on direct table subscriptions with RLS routing.**
> Hard-won lesson: Supabase Realtime `postgres_changes` can only route an event to
> a subscriber whose RLS lets them see the row — and it CANNOT reliably evaluate
> (a) a **join-based** policy (store's `order_items_manager_select`, agent's
> `try_sessions`/`order_items` rider policies) or (b) an **UPDATE that moves a row
> *into* a user's visibility** (admin assigning `deliveries.rider_id`). Both fail
> silently → "alert only goes to admin / store stopped popping". The fix everywhere:
> a DB trigger inserts a **born-visible** `notifications` row owned by the exact
> recipient, who subscribes to `notifications` INSERT filtered to their own
> `user_id` (the plain `user_id = auth.uid()` policy Realtime routes for free).
> Admin still uses `orders` INSERT directly (its policy is the simple `is_admin()`,
> which Realtime handles). Customer order-tracking uses an `id`-filtered subscription
> on its own order (born-visible). `notifications` is on the publication via 021.
